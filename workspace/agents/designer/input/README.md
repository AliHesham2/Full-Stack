# Designer input — owner-provided visual and code references

The owner may place reference material directly here or in any number of named subfolders. A folder can represent one page, one section, a design direction or a set of variants. Keep the owner's filenames and folder grouping intact; do not move or overwrite these inputs during a design task.

Supported inputs include section screenshots or photos (`.png`, `.jpg`, `.webp`, etc.), a full-page image, and HTML/CSS or React/Next.js source (`.html`, `.css`, `.jsx`, `.tsx` plus local assets). A code sample is a **reference to inspect**, not permission to execute, install dependencies, copy into the app, or infer hidden business rules. If it relies on missing styles, assets or routes, record that limitation. A full-page image may suggest visual rhythm and section order, but it cannot prove responsive behavior, interactions or accessibility.

Before designing, inventory every supplied file and subfolder in the task TODO: path, type, intended screen/section if known, visible content or code dependencies, what the owner explicitly wants matched, and any ambiguity. View images with an available image viewer at useful detail; inspect code and associated styles/assets as text. For long pages, inspect the entire image and separately inspect key regions as supported by the viewer. Do not claim visual inspection from filenames alone. If a reference mixes desktop and mobile states, identify which is which; if it shows only one viewport, specify the missing viewport behavior from requirements and guides rather than inventing it from the picture.

Extract **intent** into a structured design specification: hierarchy, layout, spacing, type, color, imagery, component anatomy, states and motion where observable. Separate facts actually visible in the input from deductions and from approved PRD requirements. Map each accepted element to a flow/screen/component and the project's semantic tokens and frontend kit. When references conflict with each other or with the approved PRD, design guide, accessibility or frontend guide, log the exact files and conflict in the Output for Orchestrator resolution. Do not silently reproduce inaccessible or unsupported details.

Keep exact source paths and reference dispositions (**inspected**, **used as inspiration**, **matched**, **rejected with reason**, **unverified**) in the authorized internal/owner-facing source record, preserving provenance. The implementation-facing Output and design TODO contain complete approved textual decisions, requirement IDs and required actual product assets, not source-picture dependencies or private source inventories. Follow [owner-preview separation](../skillz/owner-preview.md) for optional generated concept images, which must not be disclosed to Implementer at all. Resolve missing specification details before execution; do not ask Implementer to infer them from a picture. The `input/` directory remains a source inbox, not the task Output or approval record.
