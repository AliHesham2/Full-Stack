# Impeccable — Designer direction and critique adapter

The local [upstream source and reference playbooks](references/impeccable-upstream/SKILL.src.md) come from [pbakaus/impeccable](https://github.com/pbakaus/impeccable) version `4.6.0` at commit `0665bd812ae0908fcab17b96fd4f840defb882d9` (retrieved 2026-10-19), with its [Apache-2.0 license](references/impeccable-upstream/LICENSE) and [third-party notice](references/impeccable-upstream/NOTICE.md). Read a **task-relevant playbook**, not the whole catalog. This adapter makes the design methods usable by any assigned Designer without binding the role to Claude, Codex or a CLI.

## Distinct value in this project

- Classify each surface by the visitor's job: **Persuade** (decide/act), **Operate** (complete a task), **Read** (understand material), or **Experience** (explore the artifact). Use [new-work](references/impeccable-upstream/reference/new-work.md) and the applicable `mode-*.md` only when a new surface or changed visual direction is in scope. Record the mode and the reason in the task's Output, not a new global project file.
- Distinguish **refinement** (preserve established identity and behavior) from **redesign** (replace the visual system while retaining product truth and approved constraints). Missing `DESIGN.md` does not prove that no design system exists: inspect actual tokens, components and representative screens first. The approved PRD and existing kit decide whether a redesign is allowed.
- For a design-only assignment, use [shape](references/impeccable-upstream/reference/shape.md) to sharpen the user job and [critique](references/impeccable-upstream/reference/critique.md) to evaluate hierarchy, clarity and fit. Use [harden](references/impeccable-upstream/reference/harden.md), [onboard](references/impeccable-upstream/reference/onboard.md), [adapt](references/impeccable-upstream/reference/adapt.md) or [clarify](references/impeccable-upstream/reference/clarify.md) only for the relevant gap. [Craft floor](references/impeccable-upstream/reference/craft-floor.md) and [polish](references/impeccable-upstream/reference/polish.md) help critique a rendered candidate; they do not prove implementation quality by themselves.
- When a visual deliverable exists, review the actual rendered result at assigned viewports, themes and direction. Describe a concrete mismatch and the correction needed. A screenshot's appearance is not proof of keyboard, screen-reader, network or runtime behavior.

## Boundaries and handoff

The upstream skill includes a product-context engine, 24 command playbooks, detectors, browser iteration, hooks, agent helpers and write-oriented commands. Its `init`, `document`, `extract`, `live`, `generate`, `pin`, `hooks`, `doctor` and other CLI operations **do not run automatically here**. The bundled engine/scripts are not installed by this adapter; their absence does not block reading the preserved playbooks. Project truth remains in the approved PRD and its task record; visual decisions use the existing design guide, frontend kit and authorized output path rather than creating `PRODUCT.md`, `DESIGN.md`, `.impeccable/` or extra role assignments. If a CLI feature is truly needed, request a separately authorized tool/implementation assignment and verify that tool's current instructions first.

The source playbooks include implementation steps and provider-specific instructions. Treat those as reference material only. Designer specifies and reviews within its brief; Implementer owns code and Tester owns verification. Filter aesthetic recommendations through the actual product, locale, existing brand, performance and accessibility constraints. Record the selected idea, source playbook, fit, rejected alternatives if consequential, and observable acceptance evidence in the Output. Do not turn a style preference into an unapproved product requirement.
