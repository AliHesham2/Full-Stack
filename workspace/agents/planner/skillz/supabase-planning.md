5. Tie connection/pooling/prepared-statement choices to the exact driver, mode, concurrency/transaction requirements and approved limits. Name affected queries/invariants and realistic planned measurements before optimizing indexes/locks/batching/partitioning/JSONB/search. Source benchmark examples are not project performance evidence. Do not add extensions, jobs or infrastructure without scope.
6. Write exact proposed file responsibilities/order and source-supported technical choices, required verification owner/environment, blockers and change impact. Output inventories and explains these same definitions; do not create a second editable schema, copied API contract or another PRD/workflow. Its final Arabic owner explanation stays last and derives from the same canonical definitions.

An applicable source review is required before recommending readiness, but a checklist is not an audit or runtime PASS. No real project is needed to import this reusable reference. ## 4. Example limitations found during source review

Preserve upstream bytes, but do not treat its SQL/config snippets as pre-approved project code. The following are review cautions, not silently patched upstream files or newly approved production patterns:

- `security-rls-basics.md` uses a custom session setting as identity in one example. The plan must establish who can set it and how pooled/transaction context is isolated; a caller-controlled value is not trusted authentication. Privileged roles/table-owner behavior must be evaluated, not assumed covered by RLS. [PostgreSQL row security](https://www.postgresql.org/docs/18/ddl-rowsecurity.html).
- The general security checklist says UPDATE requires both clauses. Explicitly planning existing-row and proposed-row predicates is useful, but PostgreSQL can reuse `USING` as `WITH CHECK` for applicable ALL/UPDATE policies when omitted. Diagnose the effective command/role/policies, not absence of a keyword alone. [CREATE POLICY](https://www.postgresql.org/docs/18/sql-createpolicy.html).
- `security-rls-performance.md` revokes helper execution from roles while calling that helper in a policy. Validate caller execution rights, function owner/privilege behavior, search path and effective policy access before adopting such a helper; neither SECURITY DEFINER nor a private schema automatically solves authorization. Keep unsupported/contradictory choices blocked. The source's speedup examples need actual comparable evidence, not a promised multiplier.
- `conn-prepared-statements.md` contains a generic driver-option example. Do not copy `prepare: false` into node-postgres as an assumed supported setting; verify the exact driver/API and pool mode. [node-postgres queries](https://node-postgres.com/features/queries) and [Supabase connections](https://supabase.com/docs/guides/database/connecting-to-postgres) describe different relevant boundaries.
- `schema-constraints.md` includes guards based on names. Plan exact relation/schema and intended definition compatibility, existing data, ordering and concurrent execution; name existence alone is not proof that the required constraint is installed correctly.
- `monitor-explain-analyze.md` explicitly describes query execution. EXPLAIN ANALYZE is not harmless source inspection; Planner cannot run it or VACUUM/restore/advisor examples from this procedure. Plans and estimated effects remain distinct from actual authorized measurements.

These checks do not certify every example as correct for every version. When a selected rule conflicts materially with actual primary/local sources, cite both in the current proposal, identify affected items and request resolution from the actual source/decision owner. No public issue or external-project repair is implied.
