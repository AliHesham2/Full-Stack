# Implementer — project navigation, runnable handoff and owned resources

Use this from [SKILL.md](SKILL.md) during repository discovery and before handoff. It adds implementation records, not new architecture, runtime permissions or project acceptance authority.

## 1. Start and maintain the implementation project map

Before the first code edit, find the existing project-owned implementation map through the assigned task/project documentation. Reuse a suitable existing map rather than creating competing trees. If none exists, create `backend/docs/PROJECT-MAP.md` using [../templates/project-map.md](../templates/project-map.md) within the assigned project's authorized write boundary. Record its canonical path in the task TODO and Output. If that path is outside the brief's allowed writes, ask Orchestrator to supply the path/permission before dependent implementation; do not choose another hidden location. This role procedure assigns maintenance of that implementation map to Implementer, while Orchestrator records remain under their existing ownership.

The workspace guide/syntax maps route agents to knowledge; the implementation map explains the **actual application code**. Link to the approved current Planner Output, role TODO and backend project-structure guides instead of copying them. Those sources constrain architecture; the implementation map records observed layout and does not authorize it. Do not require or recreate a deleted legacy folder map merely to navigate this new route.

Build the initial tree from actual permitted repository files before planning code. Use targeted file listings such as available `rg --files` with appropriate filters, then inspect the relevant module/entry files before describing their responsibilities. Stay inside the assigned project and respect restricted paths. Exclude dependency folders, VCS internals, build/cache/coverage output, vendored source and secret-bearing files from detailed listings. Show useful configuration filenames without reading or publishing secret values. Identify existing tests and their owners without taking over their files. Missing apps are `NOT INITIALIZED`, not a fictional completed tree.

Keep a compact root tree for existing apps and important source boundaries, with one-line responsibilities. For a growing codebase, route to module sections or already-existing module documentation rather than expanding every file/function into a huge tree. Include actual entry points, major feature/domain locations, shared backend utilities, contract definitions and synchronization route, database access and migrations, tests, and relevant startup/config entry locations where they exist. For important cross-module relationships, name producer, consumer and allowed interface with source locations; folder proximity is not proof of dependency direction. Capture the actual HTTP boundary with external authorized clients without implying cross-app source imports.

Separate proposed additions in the task TODO from the map of existing files. A missing required module may be recorded as a gap, but do not create empty folders just to make the tree look complete. On every assignment, read the map first, then verify the affected branch against the actual filesystem/code; the map is a navigation aid, never a substitute for inspection. Update it during the task whenever files/modules are added, moved, renamed, deleted or change responsibility/interface. Before handoff, reconcile affected paths and links, record the inspected code revision/time and scope, and report unresolved discrepancies. Refresh wider branches when drift is observed, within authority; do not silently claim the entire map is current from a narrow check. Preserve unrelated edits and resolve concurrent map writes through Orchestrator.

## 2. Provide a runnable handoff

In the task Output, give each affected app's actual command and working directory, startup order when coupled, approved runtime/package requirements, required environment **variable names only**, configuration source/example path and external-service prerequisites. Provide the expected local URL/port or health observation from configuration, distinguishing an expected value from one actually observed. Describe fixtures or permitted local data needed to reach the changed API state without providing credentials or sensitive user data.

Use existing approved scripts and the mandatory [syntax policy](syntax-policy.md); do not invent an initialization/seed command or install missing services to fill the report. Label startup `OBSERVED RUNNING`, `FAILED`, `NOT RUN` or `BLOCKED`, with candidate, command/output evidence and limitation. A configured URL or process creation alone does not establish readiness. Document the difference between files prepared and operations actually executed. Do not assume the next operator inherits your terminal, environment variables or running service.

## 3. Track and clean up resources created by the task

Before starting a server/helper or creating temporary artifacts, record its purpose, intended project-local location, lifecycle and ownership evidence in the TODO. After creation, retain the exact process/session identity and command/working directory or resolved file path. Do not record secret command arguments; use the approved configuration route. A port number or process name alone does not establish ownership.

Reuse a running service only when authorized and its project/candidate can be established. It remains owned by its existing operator: do not stop it during cleanup. Never terminate all Node processes, kill by port alone, reset the workspace, or delete broad temporary/build directories as a convenience. Before stopping a task-owned process, verify its current identity and project association; use its graceful shutdown/session control when available. If ownership is ambiguous, leave it untouched and report the cleanup gap.

Before handoff, stop task-owned temporary processes and remove task-owned disposable artifacts when authorized and no longer needed. Preserve required evidence, candidate files and user assets. Before recursive filesystem cleanup, verify the resolved absolute target stays inside the explicitly authorized disposable location; do not follow an unexpected link or computed path outside that boundary. If cleanup fails, report the actual error and remaining resource rather than claiming success. Leave a service running only for a documented authorized handoff need, with identity, project/command, observed state, next owner/route and safe shutdown instructions in the Output. No broad process inspection/control or external-project cleanup is granted by this procedure.
