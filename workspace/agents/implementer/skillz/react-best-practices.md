# React best practices — scoped implementation and self-review

Use this procedure for assigned React/Next.js components, pages, data loading, rendering or bundle work. It is available to any Roster-assigned Implementer, without client-specific installation. Skip it for backend-only work. Continue the existing software TODO and Output; do not create another workflow, checklist file or approval gate.

## Apply only what the task needs

1. Read the affected guide and local syntax sections; inspect actual package versions, compiler configuration and component server/client boundaries. Never infer compiler coverage from a reference saying it is the default, or initialize an app to discover it.
2. From the index, select the relevant rule IDs below. Read those rule files in full, then map any chosen implementation to local syntax file/heading/version in the same software TODO. Start with avoidable request waterfalls and unnecessary shipped code when relevant; upstream impact labels prioritize inspection, not measured project severity.
3. Implement the simplest source-supported change within the approved task. Keep already-adequate code and existing libraries. Do not add SWR, `better-all`, LRU packages, analytics, compiler configuration or experimental features because an example uses them. A necessary architecture/dependency/design change goes to its established owner through Orchestrator.
4. Inspect the final diff for behavior and source conformity, then run the existing permitted checks. For an optimization claim, retain comparable before/after measurements on identified candidates with the same workload, build mode and environment. A plausible improvement without measurement remains unmeasured, not a proven speedup. No extra suite, automated E2E, test edits or tool installation is authorized here.

## Adapt upstream examples to this system

- **Architecture and data:** Keep the applicable frontend guide's HTTP boundary. In FullStack, Next.js calls Express/Node.js; in frontend-only, it consumes owner-supplied external APIs through the approved transport. Upstream `db.*`, Prisma or direct provider examples do not authorize database access from Next.js/browser, backend implementation in frontend-only, changed contracts or invented response/error shapes. Server Actions still need their prescribed boundary checks and backend authorization; a UI guard is insufficient.
- **Concurrency and caching:** Parallelize only truly independent, authorized operations, preserving error semantics, resource limits and dependency order. Never start a protected side effect before required checks. No request/user state in shared module variables. A cross-request cache requires approved identity/tenant keys, bounded lifetime/size, invalidation and logout behavior; example LRU settings are not project policy. Cached cookie presence is never authentication evidence. Do not defer required durable writes or audit delivery into best-effort `after()`/idle callbacks.
- **Existing stack and compiler:** The local data-fetching route uses its prescribed query library; SWR examples illustrate concerns, not a migration. Determine actual compiler enablement and coverage before manual memoization/hoisting; do not add/remove memoization everywhere, ignore purity or assume all effects are optimized. Keep hook ordering and complete reactive dependencies. No linter suppression to obtain an optimization.
- **Effect Events:** `advanced-event-handler-refs` describes `useEffectEvent` as having a stable reference, while `advanced-effect-event-deps` says its identity changes. Do not rely on that stable-reference claim or use Effect Events as general callback escape hatches. Use only the local version-supported, effect-scoped pattern, retain genuine reactive dependencies and stop for a source gap. [React reference checked during integration](https://react.dev/reference/react/useEffectEvent).
- **Transitions and async results:** `rendering-usetransition-loading` says new transitions cancel pending ones; this does not guarantee cancellation of network requests or correct response order. Preserve explicit stale-response/race/error handling and urgent controlled-input updates. Check local version support for updates after `await`; do not replace every loading state with a transition. [React reference checked during integration](https://react.dev/reference/react/useTransition).
- **SSR and hydration:** A browser guard alone does not prove a module is excluded from a server bundle. Check the actual import graph/build. `ssr: false` must be in the supported Client Component context, not copied into a Server Component/root layout. Treat hydration suppression as a narrow documented exception, never a fix for a mismatch. Inline-script/theme examples require existing CSP, safe serialization and consistent hydration rules; client storage never establishes an authenticated state. [Next.js reference checked during integration](https://nextjs.org/docs/app/guides/lazy-loading).
- **Observable behavior:** Preserve approved focus, accessibility, responsive layout, content, reduced motion, loading/empty/error/success states and tokens. Preloading costs bandwidth and can trigger side effects. Hidden/preserved content must obey focus and effect-lifecycle requirements; a rendering technique is not a complete dialog/menu specification. Do not move sensitive server-only data to the client to reduce duplicate serialization.
- **Micro-optimizations:** Preserve exact values, order, duplicates and errors when replacing loops, maps or validation paths. For example, `find` and a Map disagree on duplicate keys; first-error validation differs from all-errors validation; the upstream `flatMap` example can retain empty names that `filter(Boolean)` removed. Preserve accepted behavior rather than copying either snippet. Keep browser/Node support, storage failures/invalidation, cleanup and bounded memory explicit. Upstream benchmarks and universal browser/GPU claims are not measurements of this project.

Online links in this adapter document the source review, not a runtime fallback around the exclusive syntax policy. Do not silently refresh snapshots, fetch alternative code, run upstream build/install/contribution commands or activate the original auto-trigger instructions.

## Evidence in the existing TODO and Output

For relevant `I-n` items, record selected upstream rule IDs and snapshot revision, why each recommendation applies or is declined, exact local syntax/guide support and actual version/compiler evidence. Group related choices rather than reporting all 70 rules on every task. If no React/Next.js code is affected, one scoped `NOT APPLICABLE` reason suffices.

In the existing Output self-review and Checks, report actual changed locations, behavior preserved, commands/results and any comparable performance evidence or `NOT MEASURED`. Keep unsupported required choices `BLOCKED` and missing checks `NOT RUN`/`UNVERIFIED`. Tester remains the independent verification owner; Orchestrator reviews results and personally verifies repairs under the existing cycle.
