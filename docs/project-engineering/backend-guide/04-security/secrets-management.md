# Secrets & Key Management

> **Part of:** Security — Backend Project Guide
> **Read when:** Handling any credential, API key, token, signing key, encryption key, or connection string — introducing a new secret, rotating, or auditing exposure.
> **Related:** `security-foundations.md`, `../10-delivery/configuration.md`, `../08-observability/observability.md`, `../11-specialized-concerns/disaster-recovery.md`
> **Status:** Stable principles · Mechanics are platform-specific (see cloud/platform guide)

---

## 1. Definition & Inventory Discipline

A secret is any value whose disclosure breaks a security boundary: DB credentials, API keys (inbound and outbound), signing keys, OAuth client secrets, webhook signing secrets, encryption keys, service passwords, session-signing material.

Rule #1: **maintain a written inventory of every secret** — what it is, what it grants access to, where it lives, who/what consumes it, rotation cadence, and owner. Uninventoried secrets are unrotatable secrets, and unrotatable secrets are permanent breach amplifiers. The inventory itself is a protected document.

## 2. Storage — Where Secrets Live

| Tier | Approach | Notes |
|---|---|---|
| Local dev | `.env` files, git-ignored, from a committed `.env.example` with placeholders | Example file must never contain real values |
| CI/CD | Platform secret store (GitHub Actions secrets etc.), scoped per environment, masked in logs | Least-privilege: pipelines get only what they need |
| Production | Secret manager (Vault / cloud KMS-backed secret store / platform equivalent) | Injected at runtime, access-controlled, audit-logged |
| Database/app secrets | Same as production — never "hardcoded in a config table" unless encrypted with a KMS-managed key | |

Hard rules:

- **Never in source control.** Not commented, not "temporarily", not in test fixtures, not in commit history ("we'll rotate after the demo" = incident).
- **Never in artifacts** (baked into container images, bundled into client-delivered code).
- **Never in logs, errors, or traces** — redaction at the logging boundary (`../08-observability/observability.md` §6), plus tests asserting secret values don't appear in log output for flows that handle them.
- **Never in client-reachable surfaces**: API responses, error details, client config endpoints, source maps.
- Git history is forever: if a secret lands in a commit, **rotate it immediately** (history rewriting is a nice-to-have, rotation is the fix).

## 3. Configuration vs Secrets

Deployment variance (hosts, pool sizes, URLs) and secrets (credentials) are **different lifecycles**: config changes freely and is visible to more people; secrets rotate and are visible to nobody. Keep them in separate channels even if both arrive as environment variables — see `../10-delivery/configuration.md` for the config side. Anti-pattern: one giant `.env` treated as "the config," readable by every developer, containing the production DB password.

## 4. Handling Discipline at Runtime

- **Read once, inject everywhere:** secrets load at startup into the typed config (`../01-foundation/initialization.md` §2.2) and travel by reference, not by value — functions receive a client instance, never the raw key.
- **Scope each secret to one purpose**: one key per integration, per environment. The shared "master API key" used by three services is a single point of compromise with an untraceable audit trail.
- **Least privilege when creating secrets:** read-only DB users for read paths, scoped tokens (per-endpoint API keys), short TTLs where the platform allows minting on demand.
- Display discipline: mask in any UI/log (last 4 chars); never echo secrets in health checks or debug endpoints.

## 5. Encryption & Keys

- **At rest:** platform-managed encryption by default; application-layer encryption (envelope encryption: data keys under a KMS master) only for fields needing defense beyond DB-level compromise (PII vaults, tokens stored for re-use). Field-level encryption design decides what's queryable — choose columns before encrypting.
- **In transit:** TLS everywhere including internal service hops (mTLS where the platform supports it — `../03-auth/authentication.md` §5). Internal plaintext "because it's the VPC" is a 2015 assumption.
- **Key management:** keys generated by CSPRNG, stored in KMS/secret manager, **rotatable by design** (§6), never embedded in code or images. Separate keys per environment AND per purpose (a signing key for webhook payloads ≠ an encryption key for PII).
- Use vetted crypto libraries in their default-secure configurations; AES-GCM or XChaCha20-Poly1305 for authenticated encryption; never unauthenticated modes, never ECB, never custom schemes.

## 6. Rotation

- Every secret has a **rotation runbook** written before it's needed: how to introduce the new value, run dual-acceptance (both valid during the window), cut over, revoke the old, verify.
- Rotation cadence: on schedule for high-value keys (quarterly-ish is typical), **immediately** on suspected exposure, on personnel/vendor changes.
- Dual-validity windows prevent rotation-induced outages: issue new → deploy consumers → verify → revoke old. Rotations that require synchronized downtime are a design defect.
- Long-lived static secrets → prefer short-lived minted credentials where the platform offers them (cloud workload identity, database token minting, signed URLs) — the best rotation is not needing it.

## 7. Secret Sprawl Audit (Run Periodically)

- [ ] `git log -p` / secret-scanning tooling over the repo and history
- [ ] Search code for credential-shaped literals (connection strings, `AKIA`-style prefixes, `-----BEGIN`)
- [ ] Review log pipelines for unredacted secret fields (grep the logs, not the code — that's where they actually leak)
- [ ] CI job environment vs actual needs (drop unused secrets from pipelines)
- [ ] Container image layers scanned for baked-in values
- [ ] Inventory review: every secret has an owner, a purpose, and a rotation date

## 8. Failure Modes

- **The .env that conquered production:** dev-time env files promoted to prod with real credentials, readable by the whole team, never rotated.
- **Secrets in error paths:** a failed DB connection logs its connection string; a rejected API call logs headers including the Authorization value. Redact at the boundary and test for it.
- **One ring to rule them all:** single master key shared across services/environments — blast radius maximal, audit trail zero.
- **Rotation deadlock:** secrets "can't" be rotated because three legacy services hardcode them — the inventory + dual-validity design (§6) exists to prevent exactly this.
- **Client-exposed "server" keys:** API keys meant for the backend embedded in frontend builds because a generated tutorial did it that way. Any key in client-reachable code is public.
